# Jetix PM как замена ClickUp: разбор

Дата: 2026-10-10. Смотрел репозиторий `Bogersebekov/obsidian-jetix-pm`, ветка по умолчанию,
коммит `190ebc4`. Код не менял.

## Коротко

Плагин уже умеет почти всё, что мы делали в ClickUp, и формат у него удобный для агента:
одна задача = один `.md` файл с frontmatter. Новый плагин писать не нужно, готовые плагины
слабее. Не хватает одного: **канала, по которому Claude из этого проекта дотягивается до
твоего хранилища.** Локальный API плагина работает только на твоём компьютере и только пока
открыт Obsidian, а я живу в облаке. Это решается без кода в плагине: задачи лежат в git, я пишу
файлы и пушу, Obsidian у тебя подтягивает.

**Рекомендация:** брать твой плагин как есть, добавить к нему «контракт для агента» (формат
файла задачи + проверка) и хранить задачи центра в git-репозитории.

## Что это за плагин

Форк dotpm 2.5.2 (готовый плагин управления проектами для Obsidian, MIT) плюс твои добавки в
духе TaskNotes: календарь, повестка, тайм-блоки, учёт времени, режимы работы. Одна модель задачи,
одна точка записи. ~58 тыс. строк, 955 тестов на 05.10.

## Как ClickUp ложится на плагин

| В ClickUp сейчас | В Jetix PM |
|---|---|
| Папка «Продюсерский центр» | проект: заметка `Продюсерский центр.md` + папка `_tasks/` |
| Списки Команда / Клиенты / Сайт / Блог | подпроекты (плагин их умеет) или поле-список `Направление` |
| Карточка `П-N. …` | файл `_tasks/p-n-….md`, номер в `title` и в `id` |
| Статус | `status`: todo / in-progress / blocked / review / done / cancelled (свои можно задать на проект) |
| Срок | `start`, `due` в формате `YYYY-MM-DD` |
| Зависимость waiting_on | `dependencies: ["[[p-3-…]]"]`, вики-ссылка на файл задачи |
| Документ, привязанный комментарием | обычная вики-ссылка в теле задачи; документ лежит рядом в хранилище |
| Подзадачи | `parentId` / `subtaskIds` |
| Исполнитель | `assignees` (заметки людей, у каждого своя лента задач) |

Чего в ClickUp не было, а тут есть: диаграмма Ганта со стрелками зависимостей, которая сама
двигает зависимые задачи, когда блокирующая съезжает; календарь; учёт времени; экспорт любого
вида в один HTML-файл.

## Что подходит для работы агента

Проверил по коду, не по описанию:

- **Задача подхватывается по папке.** Проект собирает задачи из всех `.md` в своей `_tasks/`
  (`src/store/ProjectStore.ts`, `loadTasksFromFolder`). Новый файл не нужно прописывать в
  заметку проекта: незаписанные задачи просто встают в конец списка.
- **Зависимости по ссылке.** `dependencies` принимает вики-ссылки на файлы задач и старые id,
  плагин сам переводит их в id. Мне не нужно знать внутренние id, достаточно имени файла.
- **Мягкие значения по умолчанию.** Пропущенный `status` читается как `todo`, `priority` как
  `medium`, пустые списки как пустые (`packages/core/src/store/YamlHydrator.ts`).
- **Правки со стороны замечаются.** Если файл поменяли не через плагин (другое устройство, git,
  скрипт), плагин перечитывает проект и пересчитывает сроки зависимых задач
  (`src/jetix/tasks/externalWrites.ts`).
- **Защита от дублей id.** Если два файла получили один id, плагин сам чинит более новый
  (`src/components/IdRepair.ts`).
- **Есть API и MCP** (создать, обновить, переместить задачу, с проверкой статусов), но только на
  `127.0.0.1` при открытом Obsidian. Хорош для Claude Code на твоём компьютере, мне из облака
  недоступен.

Пример файла, который я бы писал вместо карточки ClickUp:

```yaml
---
pm-task: true
projectId: "[[Продюсерский центр]]"
id: pc-p-2
title: "П-2. Оффер для методолога"
type: task
status: todo
priority: high
start: 2026-10-11
due: 2026-10-13
assignees: ["[[Руслан]]"]
tags: [команда]
dependencies: ["[[p-1-sostav-komandy]]"]
---
Что сделать, критерий готовности.

Документы: [[Команда на старт]], [[Предложение Антону]]
```

## Чего не хватает

1. **Канал до хранилища из облака.** Главный пробел. Варианты ниже, в рекомендации.
2. **Правило в твоём же руководстве агентам запрещает писать frontmatter руками**
   (`docs/jetix/AGENT-GUIDE.md` §1: только через плагин или API). Для живого хранилища `D:\private`
   это разумно, но для облачного Claude это единственный путь. По коду ручной файл читается
   корректно; риск только в опечатке (неверный статус, битая ссылка). Закрывается проверкой, п. 3.
3. **Нет проверки файла задачи вне Obsidian.** Нужен маленький скрипт: статусы и приоритеты из
   палитры проекта, даты в формате, ссылки зависимостей ведут на существующие файлы, нет циклов,
   id уникальны. Я запускаю его перед каждым пушем. Ядро `@dotpm/core` уже умеет разбирать
   эти файлы, скрипт можно собрать на нём.
4. **Нет короткого описания формата для агента.** Сейчас формат размазан по README, `api.md` и
   AGENT-GUIDE §3. Нужна одна страница «как создать задачу файлом»: обязательные поля, правило
   имени файла и id (`p-<N>-<slug>`, `pc-p-<N>`), как ставить зависимость и привязывать документ.
5. **Нумерации П-N в плагине нет.** Не критично: номер живёт в `title` и `id`, следующий номер я
   беру по максимуму в папке.

Пункты 3 и 4 — это файлы рядом с плагином, сам плагин не меняется.

## Готовые плагины

| Плагин | Как хранит задачу | Зависимости | Сроки и вид | Удобство для агента | Итог |
|---|---|---|---|---|---|
| **dotpm** (основа твоего форка) | файл + frontmatter | да, с автосдвигом | таблица, Гант, канбан | высокое, есть API/MCP | лучший из готовых; твой форк = он же плюс календарь и время |
| **TaskNotes** | файл + frontmatter | да (`blockedBy`) | календарь, канбан, без Ганта | высокое, есть HTTP API | хорош, но ты уже перенёс из него нужное в форк |
| **Tasks** | строка-чекбокс в любой заметке, даты эмодзи | да (`🆔` / `⛔`) | только запросы-списки | среднее: правка строк внутри текста хрупкая | для личных дел, не для проекта |
| **Kanban** | весь борд — один `.md` файл со списками | нет | только борд | среднее: один файл на всех, конфликты | слабо |
| **Dataview** | не хранит задачи, только запросы | — | таблицы-запросы | — | надстройка для отчётов, не менеджер |
| **Projects** (Marcus Olsson) | файл + frontmatter | нет | таблица, борд, календарь | высокое | автор прекратил развитие в 2024 году (по памяти, не перепроверял) |

Вывод: из готовых ближе всех dotpm, и он у тебя уже есть в доработанном виде. Писать новый
плагин «как ClickUp» незачем.

## Рекомендация

1. **Плагин оставить как есть.** Изменения кода сейчас не нужны.
2. **Задачи центра хранить в git, чтобы я мог их писать.** Мой выбор — этот репозиторий
   `jetix-production-company`: он и так «единая правда» по CLAUDE.md, в нём уже лежат план и
   решения, документы будут в одном месте с задачами и ссылаться друг на друга. Папка, например,
   `pm/Продюсерский центр/` в формате плагина. У тебя: открыть клон репозитория как отдельное
   хранилище Obsidian (или подключить в рабочее) и поставить Obsidian Git с автоподтягиванием.
   Альтернативы хуже: сеанс Claude на твоём компьютере через API работает, только когда
   компьютер включён и Obsidian открыт; писать в `D:\private` значит мешать работу и личное,
   а ты решил держать Obsidian для личной жизни отдельно.
3. **Добавить «контракт для агента»:** страницу формата и скрипт проверки (пункты 3–4 выше).
   Это пара часов работы, кладу в этот проект, плагин не трогаю.
4. **Перенести 26 задач из ClickUp** файлами: П-N, сроки, зависимости, ссылки на 8 документов.
   Документы ClickUp уже частично дублированы в `docs/` этого репозитория.
